# Build plan: ADR-0025 — theme: light / dark / system (roadmap item 18)

> Generated by the `adr-plan` workflow (2026-08-26, run `wf_5ad0f042-cf8`). 11 slices,
> 5 phases, all Opus sittings. Check slices off as they land; move to
> `doc/plans/completed/` when done.
>
> Verification roster: **no slice earns an adversarial verify pass.** Every failure
> mode is visible (wrong hex, wrong contrast) or loud (typecheck, e2e); nine of the
> eleven are template copies of existing patterns (window-state field validation,
> the `registerUpdateIpc` pair, the preload wrapper). Only two carry judgment —
> `css-light-tokens` (contrast picks, plus five hard-coded hex leaks in `styles.css`
> around lines 260/396/538/562/575 that bypass the tokens today) and
> `viewport-scheme-listener` (re-run `swapContent` vs traverse materials in place;
> three.js stays inside the viewport per ADR-0008) — and a normal review covers both.
>
> Sequencing risks, named up front:
> 1. **Hex drift** — the light `--bg` is hand-copied into three places (`styles.css`,
>    main's `backgroundColor` map, `viewportPalette`). Pick it ONCE in phase 1 and put
>    the token-name comment beside every copy; the two phase-4 specs are the drift
>    guards, so phase 4 is not optional.
> 2. `nativeTheme.themeSource` must be set BEFORE `new BrowserWindow` — the flash
>    guard is an ordering fact.
> 3. `theme:set` writes the window-state file IMMEDIATELY, not only on quit, or the
>    persist spec flakes on close timing; the spec still awaits the IPC round-trip
>    before relaunch.
> 4. The header select stays OUT of the `settings` slice, so presets and Restore
>    inputs never carry it — easy to get wrong by reusing the settings pattern.
> 5. Color normalisation in both e2e specs (`#RRGGBB` vs `rgb()` vs three's
>    `getHexString`) — one shared helper.
> 6. `e2e-viewport-clear-color` likely needs a harness-facing `data-` attribute on the
>    viewport, never a three.js export.
> 7. Leave roadmap item 9's translucent-walls WON'T DO untouched in phase 5.
> 8. `/shipshape` at each phase boundary; `npm rebuild better-sqlite3` after any
>    packaging step before `npm test` (ADR-0013).

## Phases (dependency-ordered)

### 1. Foundations (main-process file field + light CSS tokens) — **opus**
_Both have empty depends_on and are independent of each other. css-light-tokens fixes the light --bg hex that phase 2's backgroundColor map and phase 3's viewport palette must mirror, so it belongs before them, not alongside. window-state-theme-field is the type every main-side slice consumes._

- [x] `window-state-theme-field` · low — `src/main/windowState.ts` already validates each field independently in readWindowState (isFiniteNumber per geometry field, maximized === true), so adding `theme` is one union type, one guard (`raw.theme === 'light' || 'dark' ? raw.theme : 'system'`), a DEFAULT_WINDOW_STATE entry, and threading the value through placeWindow/captureWindowState (captureWindowState reads from the BrowserWindow, so the current theme must be passed in or kept alongside — the only mild design point, and attachWindowState's save closure is the natural place). No theme code exists yet in src/main. tests/window-state.test.ts exists as a template for the three fallback cases (missing, unknown, valid). Pure data validation with no geometry or protocol subtlety: low effort, opus, no adversarial verify. No sibling must land first; main-native-theme-source and theme-ipc-pair consume this field, not the reverse.
      Depends on: none.
- [x] `css-light-tokens` · medium — Pure CSS: styles.css currently has one :root block (color-scheme: dark, nine tokens) and no light block, so the slice is adding a @media (prefers-color-scheme: light) redefinition plus an audit. The audit is the only real work — five hard-coded colors bypass the tokens today (line 260 #0b0e13 text-on-accent, 538 #b3261e, rgba tints at 396/562/575 built from --warn/--accent hex values) and each needs a token or a light-side counterpart. Contrast picking (WCAG AA for --text/--muted on --panel, re-chosen --warn/--error on white) is judgment but not hard reasoning; a wrong pick is visible, not silently wrong, so no adversarial verify pass. No code dependencies: it keys on the media query, which works in the renderer today under a light OS regardless of the main-process themeSource slices. Checked for contrast and hex leaks in the shipshape pass.
      Depends on: none.

_main-native-theme-source needs state.theme (phase 1) and the light --bg hex (phase 1). theme-ipc-pair needs both the field and nativeTheme setup; build them in this order within one batch since ipc's theme:get reads shouldUseDarkColors that theme-source establishes._

- [x] `main-native-theme-source` · low — Checked src/main/index.ts: no nativeTheme usage exists, so status is todo. The work is a short insertion in createWindow between the existing readWindowState/placeWindow call and new BrowserWindow: import nativeTheme, set themeSource = state.theme, compute shouldUseDarkColors, pass backgroundColor from a two-entry hex map (dark #1b1e24 already matches --bg in styles.css; light hex must agree with whatever css-light-tokens picks, kept beside a comment). The ordering constraint (set themeSource before the window exists) is already spelled out in the ADR and the file's own ADR-0014 comment pattern, so there is no subtle reasoning; the flash guard is covered by the separate e2e-theme-persist-and-flash slice rather than an adversarial pass here. Depends on window-state-theme-field because state.theme must exist on the parsed window-state type.
      Depends on: `window-state-theme-field`.
- [x] `theme-ipc-pair` · low — No theme code exists anywhere in src/ (grep is empty), so status is todo. The work is a direct copy of three existing patterns: a types-and-constants-only `src/shared/theme.ts` (like update.ts/exportFile.ts), a `registerThemeIpc()` in main mirroring `registerUpdateIpc`'s two `ipcMain.handle` calls, and a preload wrapper added to the `api` object with the `Api` type flowing into env.d.ts. It needs the `theme` field/validator in windowState.ts (window-state-theme-field) to persist against, and the main-side nativeTheme setup (main-native-theme-source) for `theme:get` to report the resolved dark/light via `nativeTheme.shouldUseDarkColors` and for `theme:set` to update `themeSource`. Shipshape applies for the commit gate (typecheck covers preload/env.d.ts; e2e slices consume this API).
      Depends on: `window-state-theme-field`, `main-native-theme-source`.

### 4. E2E coverage — **opus**
_Every spec's dependencies are satisfied after phase 3 (e2e-system-mode only needs phase 2 and could be pulled forward, but batching all three into one e2e/theme.spec.ts file and one packaged-e2e run is cheaper). e2e-viewport-clear-color may need a small test hook (data-clear-color attribute) added back into Viewport.tsx — a touch on phase 3 code, do it here._

- [x] `e2e-system-mode` · low — No theme code exists yet in src/main or src/preload (grep empty), so status is todo. The spec itself is two assertions: `app.evaluate(({nativeTheme}) => nativeTheme.themeSource)` === 'system' and `page.evaluate(matchMedia(...).matches)` === `app.evaluate(nativeTheme.shouldUseDarkColors)`. The harness (e2e/harness.ts lines 63-83) already gives every launch a fresh mkdtemp `--user-data-dir`, so profile isolation is a one-line confirmation, not new work. Depends only on main setting themeSource from the window-state file's default; no IPC or UI needed. Straightforward Playwright-Electron test, no subtle failure mode — opus, low effort, no verify pass.
      Depends on: `window-state-theme-field`, `main-native-theme-source`.
- [x] `e2e-theme-persist-and-flash` · medium — No theme code exists in src/main, preload, or renderer yet (grep empty), so status is todo. The spec is a near-verbatim reuse of e2e/window-state.spec.ts: mkdtemp profile, launchApp(args), relaunch, assert. The only thinking is (1) the "before the page paints" claim — BrowserWindow backgroundColor is fixed at construction, so getBackgroundColor() after launch is a faithful proxy; (2) normalizing the two colour representations (getBackgroundColor returns #RRGGBB; getComputedStyle(document.documentElement).getPropertyValue('--bg') may be rgb() or hex) before comparing; (3) waiting for the select's IPC round-trip to write the window-state file before closing. Mechanical-plus test work, not geometry or protocol reasoning — opus, no adversarial pass. Depends on the file field, main's themeSource/backgroundColor, the IPC pair, light tokens (so --bg differs per theme and the assert is non-vacuous), and the header select it drives.
      Depends on: `window-state-theme-field`, `main-native-theme-source`, `theme-ipc-pair`, `css-light-tokens`, `header-theme-select`.
- [x] `e2e-viewport-clear-color` · medium — Nothing exists yet: Viewport.tsx still has `const BACKGROUND = 0x1b1e24`, no matchMedia subscription, no theme IPC, and e2e/ has no theme spec. The spec itself is a standard Playwright-Electron test in the existing harness (per-launch temp profile already isolates theme): pick the header select, wait for `matchMedia('(prefers-color-scheme: dark)').matches` to flip, read `--bg` via getComputedStyle, and compare to the renderer clear color. The only real reasoning is choosing the comparison channel — the viewport keeps three.js private (ADR-0008) so the clean route is a tiny test-only hook (e.g. a `data-clear-color` attribute the island writes after re-tint) rather than sampling a SwiftShader canvas whose drawing buffer is not preserved — plus normalizing `#1b1e24` vs `rgb()` vs three's `getHexString`, and awaiting the re-tint rather than asserting synchronously. That is moderate, not hard; a wrong implementation fails loudly rather than passing vacuously, so no adversarial verify pass is needed. Depends on the palette function and listener (the thing under test), the light tokens and IPC/select (the switch mechanism). Shipshape applies at commit as usual.
      Depends on: `viewport-palette`, `viewport-scheme-listener`, `css-light-tokens`, `theme-ipc-pair`, `header-theme-select`.

Phase 4 landed as one spec, `e2e/theme.spec.ts` (5 tests), and turned up two things
worth carrying forward — both found by RUNNING it, not by reading it:

1. **Playwright emulates `prefers-color-scheme: light` on every page**, and that
   override outranks `nativeTheme.themeSource`. The first run failed with main
   reporting `themeSource: 'dark'` while the renderer stayed obstinately light —
   the app was correct and the harness was lying about it. A bare-Electron probe
   loading our own built page proved which side was wrong. `launchApp` now clears
   it (`emulateMedia({ colorScheme: null })`), beside the SwiftShader flags: same
   rule, environment quirks live in the harness and nowhere else. Any future spec
   that asserts a colour depended on this and would have measured Playwright.
2. **The flash guard has to check BOTH themes.** Pinning the opposite of the
   machine's resolved scheme — which is what keeps the spec non-vacuous under
   xvfb — exercises only one of `WINDOW_BACKGROUND`'s two hand-copied entries. A
   mutation run caught it: breaking the light hex left every test green. It is now
   a two-case loop that seeds the window-state file directly.

All five specs were mutation-tested. Each of — light `backgroundColor` drift, dark
`backgroundColor` drift, `viewportPalette` drift, `themeSource` not applied,
preference not persisted — fails at least one spec.
