# Build plan: ADR-0026 — resizable control panel (roadmap item 20)

> Generated by the `adr-plan` workflow (2026-08-26, run `wf_41e71561-e5e`). 11 slices,
> 4 phases, all Opus sittings, three commits (phase 1; phase 2; phases 3+4). Check
> slices off as they land; move to `doc/plans/completed/` when done.
>
> Verification roster: **no slice earns an adversarial verify pass.** Wrong behaviour
> is visible in the app and caught by the e2e specs; the pure functions (the clamp,
> the key-routing predicate) are pinned by vitest. The one medium-effort item is the
> drag handle, and it is textbook pointer-event wiring.
>
> Sequencing risks, named up front:
> 1. **The keyboard routing predicate must be its own function**, not undo's
>    `isEditable` — that one deliberately EXCLUDES `type=number` inputs (ADR-0016 §2),
>    while ADR-0026 §2 requires ignoring every editable element including number
>    inputs and selects.
> 2. **The persisted width passes through `clampPanelWidth` at store init AND on
>    window resize**, or a wide-monitor value pins the viewport on a laptop. The
>    re-clamp e2e must be shown to fail with the resize handler removed before it
>    counts.
> 3. Match `<` / `>` via `event.key`, with a `shiftKey` + `,` / `.` fallback — layouts
>    vary; Playwright presses use the same form.
> 4. The resize handler writes the store only ON CHANGE, so a resize does not churn
>    localStorage per event.
> 5. `/shipshape` at each phase boundary; after the packaged e2e run, `npm rebuild
>    better-sqlite3` before `npm test` (ADR-0013).

## Phases (dependency-ordered)

### 1. Foundation: clamp → store slice → CSS variable — **opus**
_A strict chain (clamp -> store slice -> CSS variable) that every control depends on. Batch as one commit: pure function + vitest, store slice copying the SETTINGS_KEY pattern + tests beside tests/settings.test.ts, and the one-line styles.css:143 swap plus the inline style on the panel. Run shipshape once at the end; existing e2e/panel-layout.spec.ts must stay green at the default 360._

- [x] `clamp-panel-width` · low — ADR-0026 Decision 4 specifies the whole function: min 280, max = min(640, windowWidth/2), NaN/non-numeric -> DEFAULT 360 (Decision 6). No code exists yet (no src/renderer/src/layout/, no clampPanelWidth references). It is a ~10-line pure function plus constants and a handful of vitest cases; the only edge worth a test is max < min on a very narrow window (windowWidth/2 < 280), which a unit test pins. No DOM, no dependencies on other slices — it is the foundation the drag, key, reset and resize slices call into. Shipshape applies for the tests-green/purity gate; no adversarial verify needed.
      Depends on: none.
- [x] `layout-localstorage-key` · low — No panelWidth / carton-fit:layout exists anywhere in src, tests, or e2e yet. store.ts already has the exact pattern to copy: SETTINGS_KEY with a try/catch localStorage.getItem at init (lines 72-99) and a setItem on write; the new key is a second instance of that with a `{ panelWidth }` shape and a non-numeric-to-default guard. It sits outside `settings` so the ADR-0016 snapshot and presets need no exclusion logic (ADR Decision 7 says so explicitly). The only cross-slice coupling is calling clampPanelWidth on load so a stale persisted value is sane, hence the dependency. Tests mirror tests/settings.test.ts (load/save/corrupt JSON). Pure wiring with a template in hand: low effort, opus, no adversarial pass; shipshape applies for the ADR-0020 doc note and test-green bar.
      Depends on: `clamp-panel-width`.
- [x] `panel-width-css-variable` · low — Verified in code: exactly one literal `width: 360px` at src/renderer/src/styles.css:143 (the other two 360 hits are comments), and no `--panel-width`/`panelWidth` exists anywhere yet. The work is a one-line CSS change to `width: var(--panel-width, 360px)` plus an inline style on the panel component reading the store slice, and a scan of the column's other width rules (the rem-sized field widths at lines 120/356/365/382/521/737 look fine; any px literal that would clip at 320px is the item-11 kind to convert). Purely mechanical wiring; the e2e-panel-layout-at-bounds slice is what catches a missed literal, so no adversarial verify pass is needed. Depends on layout-localstorage-key because the component needs the store's panelWidth to set the variable; the drag handle and keyboard slices then build on this one.
      Depends on: `layout-localstorage-key`.

### 2. The three controls — **opus**
_All three depend only on phase 1 and are independent of each other, so they can be built in one pass. Keyboard and resize listeners install together from main.tsx beside installUndoKeyboard (shared disposer pattern); the drag handle is the only medium-effort item. Manual check in the app before shipshape._

- [x] `drag-handle-resize` · medium — Nothing exists yet: styles.css still has `.panel { width: 360px }` and no pointer-capture or panelWidth code anywhere in src/renderer/src. The work is textbook pointer-event wiring — a 6px absolutely-positioned hit area, setPointerCapture on pointerdown, width = clientX - panel.left on pointermove fed through clampPanelWidth into the store, release on pointerup AND pointercancel, dblclick writes the default. Small edge cases (pointercancel, not starting a drag on non-primary buttons, avoiding text selection during drag) are well-known browser idioms, not novel reasoning, so medium effort / opus. A wrong implementation is visible instantly in the app and is covered by the sibling e2e specs, so no adversarial verify pass. It needs the clamp function, the store slice it writes to, and the CSS variable it drives to exist first.
      Depends on: `clamp-panel-width`, `layout-localstorage-key`, `panel-width-css-variable`.
- [x] `keyboard-step-binding` · low — Nothing in src/renderer/src references panelWidth yet, so this is untouched. The implementation is a near-copy of history/undo.ts: `isEditable` + `handleUndoKey` (pure, takes a KeyboardEvent-shaped object, returns boolean) + `installUndoKeyboard` (the only DOM-touching part, installed from main.tsx). The single non-copy detail is that undo's `isEditable` deliberately EXCLUDES `type=number` inputs (`target.type !== 'number'`) while ADR-0026 §2 requires this binding to ignore ALL editable elements including number inputs and selects — so the predicate must be its own function, not a reuse of undo's. Matching `event.key === '<' / '>'` (or `,`/`.` with shiftKey, since layouts vary) and calling `clampPanelWidth(current ± 40, window.innerWidth)` then writing the store slice is boilerplate. Tests follow tests/undo.test.ts with fake event objects. Needs the pure clamp and the store slice/setter to exist first. No subtle failure mode that a plausible-but-wrong implementation would hide; shipshape's test-green gate suffices.
      Depends on: `clamp-panel-width`, `layout-localstorage-key`.
- [x] `window-resize-reclamp` · low — Nothing of ADR-0026 exists yet in src/renderer/src (no panelWidth, no clampPanelWidth; only Viewport's own ResizeObserver). The slice is a ~15-line window 'resize' listener that mirrors installUndoKeyboard in history/undo.ts (target: Pick<Window,'addEventListener'|'removeEventListener'>, returns a disposer): read store.panelWidth, run clampPanelWidth(current, window.innerWidth), setPanelWidth only when changed. All the reasoning lives in the pure clamp (its own slice); this one is wiring, so low effort, mechanical, opus. The only care point is writing only-on-change to avoid churning localStorage on every resize event, which a straightforward pass handles; the resize-reclamp e2e (sibling slice) is the regression guard, so no adversarial verify is warranted. Depends on the clamp function and the store slice; run shipshape before commit.
      Depends on: `clamp-panel-width`, `layout-localstorage-key`.

### 3. E2E coverage + header review — **opus**
_All specs need every control to exist. Write panel-resize.spec.ts (restart persistence, key routing, double-click reset, resize re-clamp, plus the one canvas-tracks-stage line) and the min/max extension of panel-layout.spec.ts together; run e2e:packaged, not dev. The header guard is a diff review done in the same sitting._

The existing e2e/panel-layout.spec.ts already has the two relationship assertions as page.evaluate helpers; this slice refactors them into a helper and runs it after driving the width to 280px and to the clamped max (repeated Shift+, / Shift+. presses with body focused, or a pointer drag on the handle, then read the computed panel width to confirm the bound). That is Playwright boilerplate against a spec pattern already in the file — mechanical, low effort, opus. No subtle-bug risk: a wrong test fails loudly rather than shipping wrong behaviour. Needs the clamp, CSS variable, and a way to drive width (handle or keys) to land first; the ADR's test-isolation note means no persistence dependency. That is moderate test-authoring, not hard reasoning — opus, no adversarial pass. Status todo: no panelWidth, --panel-width, or clampPanelWidth exists in src/renderer/src yet, so this depends on every feature slice it exercises (handle/double-click, keys, resize handler, persisted key, clamp, CSS variable).
