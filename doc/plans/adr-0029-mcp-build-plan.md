# Build plan: ADR-0029 — Claude can drive Carton Fit (roadmap item 21)

> Generated by the `adr-plan` workflow (2026-09-01, run `wf_cf133787-8b6`). 14 slices,
> 6 phases: four opus sittings and two fable ones. Check slices off as they land;
> move to `doc/plans/completed/` when done.
>
> Verification roster: **exactly four slices earn an adversarial verify pass** —
> `explicit-units-wire-contract` (an imperial-units golden call through every tool;
> a missed or doubled conversion is a plausible number an AI client cannot eyeball),
> `qualified-response-schema` (prove qualifications are structurally required, not
> optionally omitted — a later fix is an ADR-0020 breaking change),
> `v2-drive-tools` (the settle-protocol race where `get_estimate` returns the
> *previous* result — a silent, plausible wrong answer), and
> `mcp-shim-single-instance` (connect-vs-lock races, pipe semantics, framing/EOF
> under proxying). Everything else fails loudly or is netted by the goldens layer —
> do not spend the pass there.
>
> Sequencing risks, named up front:
> 1. **Units + qualified-response must be settled and goldens-pinned before phase 3
>    starts**, or the fable pass builds v2 on churning schemas.
> 2. `node-occt-ingestion`'s packaged-wasm resolution may touch
>    `electron-builder.yml`'s exclusion list, which is **LGPL compliance
>    (ADR-0011)** — any change there re-runs the compliance suite, not just
>    `e2e:packaged`.
> 3. `hidden-launch`'s window-all-closed carve-out alters normal quit behaviour;
>    verify the plain desktop app still quits cleanly *before* phase 5 stacks the
>    pipe listener on the same path.
> 4. The shim's single-instance lock affects **every** launch, MCP or not — dogfood
>    a normal double-launch, and check it on Windows CI (the pipe behaviour cannot
>    be fully proven on the WSL dev box).
> 5. `connect-to-claude-button` must not ship in any staged build before the shim
>    exists, or a dogfooder's Claude Desktop config points at a flag the binary
>    doesn't have.
> 6. `/shipshape` at each phase boundary; after any packaged e2e run,
>    `npm rebuild better-sqlite3` before `npm test` (ADR-0013).

## Phases (dependency-ordered)

### 1. Foundations: SDK adoption + Node-side STEP ingestion — **opus**
_Both have zero dependencies and everything else needs at least one of them. One
batch, either order._

- [ ] `mcp-sdk-dependency` · low — Pure adoption wiring: install the MCP TypeScript
      SDK, add its MIT notice row to THIRD-PARTY-NOTICES.md, extend CLAUDE.md's
      runtime-dependency list, confirm bundled-in-app means no new packaging path.
      ADR-0029 is itself the dependency ADR the convention requires;
      `e2e/licence-notices.spec.ts` already parses the notices table, so a missing
      citation fails an existing test. Care point: check the SDK's licence-file path
      in node_modules and eyeball its transitive deps.
      Depends on: none.
- [ ] `node-occt-ingestion` · medium — Factor what already exists into a real
      main-process module (readFile → ReadStepFile → extractParts → core pipeline):
      `tests/golden-parse.test.ts` already instantiates occt under plain Node with
      the hand-computed AS1 oracle, and `occt-to-parts.ts` is pure TS reusable
      verbatim. The genuine edge is **packaged** wasm resolution: electron-builder
      excludes the node_modules copy of occt's glue/wasm (the asarUnpack'ed copy is
      the only one shipped, and that exclusion list is ADR-0011 compliance), so the
      dev-mode "no locateFile" story does not hold in the packaged main process —
      see sequencing risk 2.
      Depends on: none.

### 2. v1 tool surface + wire contract, pinned by goldens — **opus**
_Produces a finished, proven v1 contract before any fable work starts. Internal
order: v1 tools first; units + qualified-response as one edit pass over the same
schemas; then the goldens layer pins the whole surface (SDK in-memory transport —
no server host needed)._

- [ ] `v1-inspect-tools` · medium — `inspect_model` + stateless `estimate` as thin
      adapters; the ADR forbids new packing/geometry logic and the seams exist
      (PackRequest/PackResult, meshVolume/isClosedMesh, pure pack entry). The one
      subtlety: `packing/request.ts` is store-coupled, so the stateless estimate
      needs a small extraction to mirror the mode/quality/constraints contract
      (inner-dims mm, ADR-0018 overrides, sanitized clearances, binding + upper
      bound) without duplicating logic. Contract mistakes are netted by the goldens
      slice, by design.
      Depends on: `mcp-sdk-dependency`, `node-occt-ingestion`.
- [ ] `explicit-units-wire-contract` · medium · **verify** — Units required in every
      tool's input schema and tagged on every echoed value, both directions.
      Conversion math exists in `core/units.ts`; the design edge is ADR-0024's
      decoupling (weight units independent of the length system), so a single naive
      `units` field would be wrong by design. Verify pass: an imperial-units golden
      call through each tool.
      Depends on: `mcp-sdk-dependency`, `v1-inspect-tools`.
- [ ] `qualified-response-schema` · medium · **verify** — Structured qualifications
      in every response (binding constraint, upper bound beside placed count,
      warnings) plus the ADR-0028 ceiling/fill-trial language in `estimate`'s
      description. Core's `upperBound` is optional (absence-over-misinformation),
      so a single pass could plausibly ship a schema where a qualification silently
      omits — the exact "never received them is our bug" failure. Verify that
      qualifications are structurally required.
      Depends on: `v1-inspect-tools`.
- [ ] `goldens-third-consumer` · medium — The MCP tools become the goldens' third
      consumer (ADR-0005): load sample → call tool → assert `samples/goldens.ts`
      hand-computed expectations, on the template of `tests/golden-parse.test.ts`.
      The compliance half is confirm-only (the LGPL substitution spec already
      corrupts/restores the shared wasm). This slice IS the verification layer for
      phase 2's contract — landing it here, not later, catches contract mistakes
      before phase 3 builds on those schemas.
      Depends on: `v1-inspect-tools`, `explicit-units-wire-contract`,
      `qualified-response-schema`.

### 3. Fable batch A: server host + drive tier — **fable**
_The two big architecture slices. Host first, then drive tools on top. v2's schemas
are already fixed by phase 2, so this pass solves lifecycle/async problems, not
contract design._

- [ ] `mcp-server-host-in-main` · high — The protocol is SDK-handled; the real
      difficulty is the packaged-runtime entry mode: a second electron-vite build
      entry executed via `ELECTRON_RUN_AS_NODE`, where Electron APIs are absent,
      module resolution must work from inside/around app.asar, and the asarUnpacked
      OCCT wasm must stay reachable — the exact dev-green/packaged-broken class
      ADR-0005 exists for. The transport/handler seam is load-bearing for all three
      tool tiers and the HTTP/CLI revisit trigger. Failures are loud;
      `e2e:packaged` is the net.
      Depends on: `mcp-sdk-dependency`.
- [ ] `v2-drive-tools` · high · **verify** — Reads as thin adapters, but the store,
      undo stack, auto-pack subscription, and capture seam are renderer-side while
      the server is in main: this slice invents a main-to-renderer request/response
      bridge (a new IPC direction) plus an async **settle protocol** — after
      `set_inputs`/`load_model`, the tool must wait through autoPack's debounce, the
      worker round-trip, and the staleness filter, or `get_estimate` returns the
      PREVIOUS result: a race that produces a plausible number and ships silently.
      `capture_view` adds the hidden/throttled-window WebGL read-back edge. Undo
      integration comes free via restoreInputs-style actions.
      Depends on: `mcp-sdk-dependency`, `mcp-server-host-in-main`,
      `v1-inspect-tools`, `explicit-units-wire-contract`, `qualified-response-schema`.

### 4. Lifecycle polish + data tier + version handshake — **opus**
_Four slices layering on phase 3's host and bridge; mutually independent — batch
freely._

- [ ] `stdout-protocol-discipline` · low — src/main has no stdout-bound console
      calls today (storage.ts uses warn/error → stderr under Node), so this is a
      small guard keyed off the server-mode flag: redirect console.log/info to
      stderr, guard against future strays. A corrupted stream breaks the first
      handshake instantly — loud.
      Depends on: `mcp-server-host-in-main`.
- [ ] `hidden-launch-show-on-drive` · medium — Server-mode flag suppresses
      `win.show()`; first drive-tier call shows the window. Three index.ts
      lifecycle interactions lift it above mechanical: `startUpdateCheck()` is
      gated on the window showing (ADR-0021 §2) and needs a decision for hidden
      boots; `window-all-closed` quits — which in server mode would kill the server
      Claude Desktop still holds (carve-out or recreate-on-demand); and the
      maximize-before-show/windowState sequencing must survive a deferred show.
      See sequencing risk 3.
      Depends on: `mcp-server-host-in-main`, `v2-drive-tools`.
- [ ] `v3-data-tools` · medium — Seven tools, every one a thin adapter over a seam
      that exists: preset/estimate lists via main's own db functions;
      apply/restore/save via the renderer functions that already carry ADR-0016/0018
      semantics, riding the v2 bridge ("through the store actions, never a side
      door"); exports via the pure builders on `collectExport()`, returning the
      string and skipping the dialog path.
      Depends on: `mcp-server-host-in-main`, `v2-drive-tools`,
      `explicit-units-wire-contract`.
- [ ] `one-version-handshake` · medium — `app.getVersion()` (with `+sha` when
      staged, per ADR-0027) into the SDK's serverInfo and a version field in
      `get_app_state`, plus the doc amendment folding tool schemas into ADR-0020's
      surface. The non-trivial part: ADR-0027 §4 keeps the internal version string
      clean and `src/main/version.ts` rejects build suffixes, so the `+sha` form is
      composed at build time (electron-vite define) without touching either.
      Depends on: `mcp-server-host-in-main`, `v2-drive-tools`.

### 5. Fable batch B: --mcp shim + single-instance pipe — **fable**
_Deliberately isolated: the highest-risk slice in the plan. Follow with a
normal-launch dogfood pass and a Windows CI check._

- [ ] `mcp-shim-single-instance` · high · **verify** — Genuine lifecycle/IPC
      reasoning: the shim's connect-vs-lock decision races concurrent launches; the
      pipe must work as both a Windows named pipe and a Unix socket (stale-socket
      cleanup, userData-scoped naming); stdio proxying must preserve MCP framing,
      backpressure, and EOF; the manual-second-launch path must route the lock to
      show the hidden instance's window; and quit-while-shim-held is the policy the
      ADR punted here. Every one of these has a happy-path implementation that
      silently forks reality — the exact failure the ADR exists to prevent. Risk is
      high because the lock and pipe listener change the normal desktop launch path
      for every user. See sequencing risk 4.
      Depends on: `mcp-server-host-in-main`, `hidden-launch-show-on-drive`.

### 6. Connect to Claude button — **opus**
_Last on purpose: the config entry it writes IS the shim's launch contract._

- [ ] `connect-to-claude-button` · medium — Per-OS config-path resolution,
      read-**merge**-write of `claude_desktop_config.json` (never clobber other
      mcpServers entries; tolerate missing/malformed config), packaged
      `process.execPath` + `--mcp` vs dev launch, "Claude Desktop not installed"
      UX. In-repo templates for every piece (theme.ts/updateCheck.ts main-side,
      UpdateBanner/SaveEstimateButton renderer-side). Failure is loud — Claude
      Desktop won't connect. See sequencing risk 5.
      Depends on: `mcp-shim-single-instance`.

## Critical path

`node-occt-ingestion` → `v1-inspect-tools` → `explicit-units-wire-contract` →
`v2-drive-tools` → `hidden-launch-show-on-drive` → `mcp-shim-single-instance` →
`connect-to-claude-button`. The parallel `mcp-sdk-dependency` →
`mcp-server-host-in-main` branch (high-effort fable) converges at `v2-drive-tools`
and gates phase 3 equally — treat the host as co-critical when scheduling.
